AI 试炼场的多机协作与部署思路

围绕多机分支协作、GitHub 同步和博客部署方式，整理一套更适合 AI 试炼场的工作流。

[SYS.LOG] > Synchronizing workflows across nodes.

AI 试炼场后面会持续记录模型生成的网站、文章、实验过程和整理结果，因此内容来源不会只来自一台机器，也不会只来自一个人手工编辑。

比较自然的演进方式是：多台机器各自产出内容，通过 GitHub 汇总，再由一条受控的发布链路完成部署。

目标

  • 让多台机器都能产出内容并同步到同一个仓库。
  • 保持服务器不直接暴露给每一台机器。
  • 让部署入口尽量单一，避免状态漂移。
  • 保留审查和回滚能力。

多机协作分支模型

一个比较稳的方式是给每台机器一个长期分支，例如：

  • machine/macbook
  • machine/workstation
  • machine/server-lab

每台机器上的模型产出、草稿整理、配置试验，都先落在自己的分支上。这样做的好处是：

  • 机器之间不会直接相互覆盖。
  • 容易追踪某一类内容是在哪台机器上产生的。
  • 某台机器的试验性改动不会直接污染发布分支。

真正对外发布时，只允许 main 作为发布源。这样 GitHub 就是唯一的汇总点，服务器不需要面对来自多台机器的直接写入。

如果后面内容量变大，还可以再加一层约束：

  • main 只放已经确认可发布的内容。
  • machine/* 只做同步和草稿。
  • 需要发布时，通过 PR 或手动 merge 进入 main。

方案演进与对比

方案一：直连服务器部署 (不推荐)

这是最直接的方式。每台机器生成静态文件后，直接推到服务器，或者直接 SSH 到服务器执行更新。

缺陷：每台机器都要持有服务器凭据，暴露面随着机器数量增长而扩大。很难保证发布入口一致，一旦某台机器状态脏了，可能直接把问题带到线上。

方案二：GitHub Actions 自动部署 (当前方案)

这是静态站点（如当前的 Astro 架构）最自然且受控的方案。

基本链路：

  1. 每台机器把内容推到自己的分支。
  2. 需要发布的内容通过 PR 合并到 main。
  3. GitHub Actions 在 main 更新后执行 npm run build。
  4. 产出物（dist/）自动部署到目标环境（如 GitHub Pages）。

优势：

  • 所有机器都不需要直接接触部署凭据。
  • 发布入口统一，审计记录清晰。
  • 回滚、重跑、对比构建结果都比较方便。

方案三：自建推送服务 (未来演进)

服务器上跑一个受控服务，通过鉴权 token 接收发布请求，再触发仓库更新和构建。这适合后续不仅有静态博客，还有需要运行复杂环境的模型产出物时使用。这被视为我们系统的“第二阶段”。

当前落地方式

由于本站已经彻底迁移至 Astro 框架，并且去除了老旧的 Hexo 依赖，我们当前的落地方式非常清晰、轻量：

  1. 多台机器各自使用 machine/* 或 feature/* 分支同步源码内容。
  2. 需要上线的内容通过 PR 提交至 main。
  3. 借助 GitHub Actions，当代码合并进 main 分支后，自动执行 Node 构建流。
  4. 构建产出的 dist/ 静态资源目录将通过内置的 deploy action，自动发布至 gh-pages 分支。

这套机制的核心，不再是“怎么把文件传上去”，而是“怎么让多终端模型产出在协作下仍然可控、可审计、可回滚”。
