AI 试炼场的多机协作与部署思路

  • ai
  • deployment
  • github
  • workflow

AI 试炼场后面会持续记录模型生成的网站、文章、实验过程和整理结果，因此内容来源不会只来自一台机器，也不会只来自一个人手工编辑。

比较自然的演进方式是：多台机器各自产出内容，通过 GitHub 汇总，再由一条受控的发布链路完成部署。

目标

  • 让多台机器都能产出内容并同步到同一个博客仓库。
  • 保持服务器不直接暴露给每一台机器。
  • 让部署入口尽量单一，避免状态漂移。
  • 保留审查和回滚能力。

多机协作分支模型

一个比较稳的方式是给每台机器一个长期分支，例如：

  • machine/macbook
  • machine/workstation
  • machine/server-lab

每台机器上的模型产出、草稿整理、配置试验，都先落在自己的分支上。这样做的好处是：

  • 机器之间不会直接相互覆盖。
  • 容易追踪某一类内容是在哪台机器上产生的。
  • 某台机器的试验性改动不会直接污染发布分支。

真正对外发布时，只允许 main 作为发布源。这样 GitHub 就是唯一的汇总点，服务器不需要面对来自多台机器的直接写入。

如果后面内容量变大，还可以再加一层约束：

  • main 只放已经确认可发布的内容。
  • machine/* 只做同步和草稿。
  • 需要发布时，通过 PR 或手动 merge 进入 main。

方案一：每台机器直连服务器部署

这是最直接的方式。每台机器生成静态文件后，直接推到服务器，或者直接 SSH 到服务器执行更新。

优点：

  • 路径最短。
  • 排查问题时比较直接。
  • 不依赖 GitHub Actions。

缺点：

  • 每台机器都要持有服务器凭据。
  • 服务器暴露面会随着机器数量增长而扩大。
  • 很难保证发布入口一致。
  • 一旦某台机器状态脏了，可能直接把问题带到线上。

如果这是一个长期运行、多人或多机都可能参与产出的博客，这个方案不适合作为默认方案。

方案二：GitHub Actions 自动部署

这是静态博客最自然的方案之一。

基本链路可以是：

  1. 每台机器把内容推到自己的分支。
  2. 需要发布的内容合并到 main。
  3. GitHub Actions 在 main 更新后执行构建。
  4. 构建产物自动部署到目标环境。

部署目标可以有几种：

  • GitHub Pages
  • 服务器上的静态目录
  • 对象存储 + CDN

优点：

  • 所有机器都不需要直接接触服务器。
  • 发布入口统一，审计记录清晰。
  • 很适合静态站点。
  • 回滚、重跑、对比构建结果都比较方便。

缺点：

  • 需要维护 CI 配置。
  • 如果部署到自建服务器，仍然需要在 GitHub Secrets 中保存某种凭据。
  • 某些复杂的服务端逻辑不如自建发布服务灵活。

如果 AI 试炼场本质上还是一个 Hexo 静态博客，这个方案通常是默认推荐。

方案三：自建推送服务

你提到的方式是服务器上跑一个 chattool serve 风格的服务，通过鉴权 token 接收发布请求，再触发仓库更新、构建和切换。

这个方案的核心思路其实不是让每台机器去碰服务器，而是让服务器只暴露一个受控的发布入口。

优点：

  • 可以把部署逻辑全部集中到服务端。
  • 可以做更细的鉴权、审计、限流和灰度。
  • 可以扩展成“接收 GitHub Webhook 后自动拉取部署”。
  • 后面如果不仅是博客，还想部署别的模型产出网站，也比较容易复用。

缺点：

  • 需要自己维护服务的安全性和稳定性。
  • 需要处理 token、重放防护、日志、失败重试等细节。
  • 系统复杂度高于纯 GitHub Actions。

这个方案更适合作为第二阶段，而不是第一阶段。

更推荐的组合方式

如果要兼顾安全、简单和可扩展，我更推荐下面这个组合：

  1. 多台机器各自使用 machine/* 分支同步内容。
  2. main 作为唯一发布分支。
  3. GitHub 作为唯一协作和汇总入口。
  4. 部署只从 main 触发。

在“部署只从 main 触发”这个前提下，可以再分成两种落地方式：

组合 A：GitHub Actions 直接部署

适合场景：

  • 你希望先快速稳定地跑起来。
  • 站点本质就是静态文件。
  • 服务器侧不想额外维护一个发布服务。

推荐度：高。

组合 B：GitHub Actions 只负责触发，自建服务负责部署

链路是：

  1. main 更新。
  2. GitHub Actions 通过受控 token 调用服务器上的部署接口。
  3. 服务器自己 git pull、npm ci、hexo generate、切换静态目录。

这样做比“每台机器直连服务器”安全很多，因为真正接触服务器的只有 GitHub Actions 和服务器本身。

推荐度：中高。

如果以后 AI 试炼场不仅发布博客，还会发布多个模型生成站点，这个方向会更有扩展性。

不建议的形态

不太建议让每台机器都各自持有服务器部署权限，然后从本地直接上线。

问题不只是安全，还包括：

  • 发布行为不可控。
  • 很难知道线上版本到底来自哪台机器。
  • 很难复现和回滚。
  • 一旦某台机器构建环境不同，线上结果可能就不同。

当前阶段的建议

如果现在的重点是先把 AI 试炼场稳定运行起来，我会建议：

  1. 先采用“多机分支 + GitHub 汇总 + main 发布”的模型。
  2. 第一阶段优先使用 GitHub Actions 做构建校验，并由 Actions 调用服务器上的 deploy hook。
  3. 等后面模型生成的网站种类更多、部署链路更复杂时，再把 deploy hook 扩展成统一发布服务。

换句话说：

  • GitHub 负责协作和汇总。
  • main 负责发布语义。
  • Actions 负责构建校验和受控触发。
  • 服务器 deploy hook 负责最终部署和回滚控制。

本站准备采用的落地方式

AI 试炼场当前准备采用更接近传统 Hexo 和 butterfly 旧站的方式：

  1. 多台机器各自使用 machine/* 分支同步源码内容。
  2. 需要上线的内容合并到 main。
  3. git push 负责同步源码仓库。
  4. hexo d 负责部署构建后的静态站点。
  5. hexo d 使用标准 hexo-deployer-git 将 public/ 推送到部署目标。
  6. GitHub Actions 也复用同一条 hexo d workflow。

这样做的关键点是：

  • 源码同步和网站部署是两回事。
  • 部署对象是构建产物，不是源码仓库。
  • 本地和 CI 走的是同一套部署语义。
  • 部署更新天然保留 Git 差量特性。

如果后续需要更强的服务端统一控制，再把 deploy hook 作为第二阶段扩展即可。当前默认方案优先保持简单。

后续可以继续细化的点

  • 分支命名规范
  • PR 合并规范
  • 自动构建和预览环境
  • 服务器上的目录切换与回滚策略
  • 文章与模型产出的目录组织方式

这套机制的核心，不是“怎么把文件传上去”，而是“怎么让模型产出在多机协作下仍然可控、可审计、可回滚”。
